# CLAUDE.md

## Build & test

```
make build          # builds bin/bewitchd and bin/bewitch
make deb            # build Debian package (requires dpkg-buildpackage)
go build ./...      # compile check all packages
go vet ./...        # static analysis
make test           # run all unit tests (go test ./...)
make test-verbose   # run tests with verbose output
make test-integration  # run integration tests requiring DuckDB (go:build integration)
```

The project targets Linux (procfs/sysfs); it compiles and tests pass on macOS but collectors won't function. Tests are table-driven, colocated with source (`*_test.go`), and avoid filesystem/sysfs dependencies so they work cross-platform.

**Test coverage by package:**

- `internal/db` — migration runner (fresh DB, existing DB detection, dirty state, idempotent restart), unique-rule-name dedup migration, and a driver-pitfall guard asserting DuckDB's `LastInsertId()` returns `0` (so code uses `RETURNING id`)
- `internal/config` — config parsing, duration handling, interval clamping, disk excludes, collector enable/disable, TLS config validation, auth config validation
- `internal/alert` — linear regression, glob-to-SQL, threshold comparison, query building
- `internal/collector` — CPU delta computation, physical device mapping, SMART parsing (NVMe + ATA)
- `internal/api` — JSON round-trips, history bucket scaling, cache keys, query source routing, read-only SQL validation via DuckDB statement types, self-signed cert generation and persistence, bearer token auth middleware and AuthTransport, alert-rule CRUD handlers (create-links-config, update-in-place, type-lock, name-uniqueness 409, rename rewrites alerts, delete clears alerts) on a real migrated DB, and an **end-to-end alert pipeline test** (`alert_pipeline_test.go`: create via handler → seed breaching metrics → `Engine.EvaluateOnce()` → assert an alert fires) that crosses the API-write/engine-read seam
- `internal/tui` — byte/bit formatting, bar rendering, status bar, time labels, process sorting, age formatting, known_hosts round-trip; teatest-based UI tests for view switching, tab cycling, history range, dynamic tab hiding, and process view interaction via `mockClient` implementing the `daemonClient` interface; alert form round-trip + edit/delete-confirm/ack interaction tests; and a **client contract test** (`client_contract_test.go`) driving the real `DaemonClient` against the real API handlers over `httptest` (via `api.Server.Handler()`) so client/server drift is caught
- `internal/repl` — value formatting, column width computation, table rendering, byte formatting, EXPLAIN output rendering, export arg parsing

## Project structure

```
cmd/bewitchd/       — daemon entrypoint (collection loop, API, alerts, pruner, archiver)
cmd/bewitch/        — TUI entrypoint (bubbletea app)
internal/config/    — TOML config parsing
internal/db/        — DuckDB connection, schema migrations (applied on startup)
internal/collector/ — metric collectors (CPU, memory, load average, disk, network, ECC, temperature, power, GPU, process)
internal/store/     — writes collected samples to DuckDB; archive.go handles Parquet export
internal/alert/     — alert engine (threshold, predictive, variance rules; DB-stored; email/command delivery)
internal/api/       — HTTP API over unix socket + optional TCP (status, alerts, config, history), JSON serialization
internal/tui/       — bubbletea views (dashboard, cpu, memory, disk, network, hardware, process, alerts)
internal/repl/      — interactive SQL REPL (readline-based, queries daemon via POST /api/query)
debian/             — Debian packaging (control, rules, postinst, postrm, systemd service)
```

## Key conventions

- **Collector interface**: all metric collectors implement `collector.Collector` (Name + Collect methods). Each returns a `collector.Sample` with typed data. Collectors that need configuration (e.g., exclusion patterns) accept it via constructor parameters. The process collector constructor takes `(maxProcs int, configPins []string)`.
- **Collector intervals**: each collector has a configurable `interval` field in its `[collectors.*]` TOML section (e.g., `[collectors.cpu]` `interval = "1s"`). If omitted, falls back to `[daemon]` `default_interval` (default 5s). Minimum 100ms. All eight collectors have config structs with `GetInterval(defaultInterval)` methods. The daemon uses a GCD-based tick scheduler: it computes the GCD of all collector intervals, ticks at that rate, and fires each collector when `tickCount % tickMod == 0`. `computeTickInterval()` (in `cmd/bewitchd/main.go`, unit-tested) **floors the tick at `minTick` (100ms)** so coprime sub-second intervals (whose GCD can be a few ms, e.g. `gcd(100ms,105ms)=5ms`) can't spin the scheduler at thousands of wakeups/sec; when the floor engages it logs a WARN and each collector's cadence is approximated to the nearest tick multiple (`tickMod` is guarded ≥ 1). Round intervals (1s, 5s, 30s) share a clean divisor and never hit the floor.
- **Collector enable/disable**: temperature and power collectors can be disabled via `[collectors.temperature]` and `[collectors.power]` config sections with `enabled = false`. Uses pointer bool (`*bool`) to distinguish "not set" (defaults to enabled) from "explicitly disabled". See `config.TemperatureCollectorConfig.IsEnabled()` and `config.PowerCollectorConfig.IsEnabled()`.
- **Collector filtering**: the disk collector filters mount points by prefix (default excludes: `/snap/`, `/run/`). Config is in `[collectors.disk]` section; see `config.DiskCollectorConfig` and `config.DefaultDiskExcludes`.
- **SMART health data**: the disk collector reads SMART data per physical device, cached with a configurable `smart_interval` (default 5m, min 30s). It is shown live (in `DiskMetric`) **and** persisted: on each cache-refresh cycle the collector emits `DiskData.SMART` (`[]SMARTDevice`, deduped per physical device) and the store writes a slim row to the `smart_metrics` table (migration `000010`, device name denormalized) — so SMART trends over months are queryable via the REPL and alertable. Because `DiskData.SMART` is populated only on refresh cycles, persistence happens at the `smart_interval` cadence, not every disk tick. Alert metrics aggregate across all devices (worst value over the window, no per-device scope): `smart.reallocated`, `smart.pending`, `smart.uncorrectable`, `smart.percent_used` (NVMe wear), and `smart.unhealthy` (count of SMART health failures — the "your disk is dying" signal). `physicalDevice()` strips partition suffixes (NVMe `pN`, SATA trailing digits) so multiple mounts from the same disk share one SMART read. The `DiskCollector` constructor takes `(excludeMounts []string, smartInterval time.Duration)`. SATA devices read attrs 5/197/198/1; NVMe reads `AvailSpare`, `PercentUsed`, `CritWarning` from the health log.
- **SMART data sources**: the disk collector prefers `smartctl` (smartmontools) when available, detected once at startup via `exec.LookPath`. If smartctl fails for a specific device, falls back to `anatol/smart.go` library, then direct SAT passthrough (`sat_linux.go`). Fallback is per-device, not global. smartctl is NOT a hard dependency. smartctl execution uses a 30-second timeout to avoid blocking on degraded devices. Requires `CAP_SYS_RAWIO` capability for direct device access (both smartctl and library paths).
- **Rate metrics**: disk I/O, network, power, and process collectors keep previous readings in memory and compute deltas. First sample after startup is discarded.
- **Parallel collection**: collectors due on each tick run concurrently via goroutines, reducing total cycle time. Results are gathered with `sync.WaitGroup` before API cache push. Collectors not due on a given tick produce nil samples, which `WriteBatch` skips.
- **Decoupled write pipeline**: after each collection tick, the daemon pushes metrics to the API cache immediately (so the TUI always sees fresh data), then enqueues samples to a buffered channel (capacity 8) for asynchronous DB writing. A dedicated writer goroutine drains the channel and calls `WriteBatch`. If the channel is full (writer slower than collector), the batch is dropped with a warning. On shutdown, the channel is closed and drained before the DB connection closes.
- **Collector backoff**: when a collector's `Collect()` returns an error, consecutive failures trigger exponential backoff. The collector skips `2^(n-1)` intervals (capped at 64×) before retrying. On success, the failure count resets immediately. First error is always logged; subsequent errors include attempt count and backoff duration. Recovery is logged at INFO level. Backoff fields (`consecutiveFails`, `skipUntilTick`) live on `scheduledCollector` in `cmd/bewitchd/main.go`.
- **DuckDB concurrency**: daemon uses a connection pool (`SetMaxOpenConns(4)`) to allow API handlers to execute concurrently with batch writes. TUI opens a separate read-only connection. During pruning/compaction (and per-day archive deletes), the store buffers incoming writes in memory (`s.buf`) and flushes them on `resume()`. The buffer is capped at `maxBufferedSamples` (2048) via `bufferLocked()`, dropping oldest samples with a warning if exceeded — a safety net so an unexpectedly long pause cannot grow it without bound and OOM the daemon.
- **Batch writes with Appenders**: `WriteBatch()` uses DuckDB's Appender API for high-performance bulk inserts. To avoid deadlock with the single connection, writes use a 3-phase pattern: (1) SQL operations (dimension/process_info inserts), (2) acquire driver connection, (3) appender writes only. Phase 3 must never call SQL methods.
- **DuckDB checkpointing**: WAL checkpoints are handled automatically by DuckDB via `wal_autocheckpoint` (configurable via `checkpoint_threshold`, default 16MB). For crash safety, `checkpoint_interval` can be set (e.g., `5m`) to force periodic checkpoints regardless of WAL size, ensuring data is flushed to the main database file.
- **DuckDB memory limit**: `db.Open()` always sets a DuckDB `memory_limit` (config `[daemon] db_memory_limit`, default `512MB` via `config.DefaultDBMemoryLimit` / `DaemonConfig.DBMemoryLimitValue()`). DuckDB's own default is ~80% of physical RAM, which is far too much for a background monitoring daemon and was the proximate cause of OOM kills on small hosts — so the empty/unset case must never fall through to it. A `temp_directory` (`duckdb_tmp` next to the DB file, created on Open) is set alongside so large sorts/exports spill to disk instead of OOM. Tests/TUI may pass `""` to skip both.
- **Data pruning**: if `retention` is configured, the daemon periodically deletes old rows from metric tables (configurable via `prune_interval`, default 1 hour).
- **Compaction**: full database rebuild to reclaim fragmented space. Can be scheduled via `compaction_interval` or triggered manually via `POST /api/compact`. Pruning, compaction, and archiving are mutually exclusive (coordinated via mutex). **Reader/restart safety**: the close→rename→reopen swap runs under `s.mu` so a reader in `Store.DB()` sees either the fully-old or fully-new `*sql.DB` (the reassign previously raced `DB()`'s read; `Close()` waits for in-flight queries so they finish before the rename). The reopen goes through `db.Reopen()`, which re-applies the runtime settings (`memory_limit`/`temp_directory`/`wal_autocheckpoint`/parquet cache) — these are per-DuckDB-instance and would otherwise reset to defaults (notably ~80%-RAM `memory_limit`) on the fresh pool; the daemon records them via `Store.SetCompactionReopenOptions()`. The original file is renamed to `<db>.pre-compact` during the swap; `db.Open()` calls `recoverInterruptedCompaction()` on startup to restore it if the process died mid-swap (otherwise a missing main file would silently open as an empty DB).
- **Parquet archival**: if `archive_threshold` and `archive_path` are configured, data older than the threshold is exported to daily Parquet files (zstd compressed) and deleted from DuckDB. History API queries automatically union DuckDB and Parquet data based on the requested time range. Archive state is tracked in the `archive_state` table. Dimension tables (`dimension_values`, `process_info`) are snapshotted to Parquet on each archive run. Old Parquet files are pruned based on `retention`. **Archive must not lock up the daemon**: `Archive()` does NOT hold a single `pause()` across the whole run. Exports are read-only (they only touch data older than the cutoff) and run concurrently with live collection; only the small per-day `DELETE` + `archive_state` update runs under a brief `withPause()`. Work is committed one day at a time, so an interrupted run resumes from the last fully-committed day. Export queries deliberately omit `ORDER BY ts` (Parquet needs no sorted input; sorting whole days was a memory hog). The earlier whole-table, whole-run-paused implementation buffered all incoming samples into `s.buf` for the duration and OOM'd/froze on a first archive of a large DB.
- **Schema migrations**: versioned SQL files in `internal/db/migrations/` (embedded via `//go:embed`), applied automatically on startup by the migration runner in `internal/db/migrate.go`. Version tracked in `schema_version` table. Go-function migrations supported for data transforms (e.g., `migrateAlertRules` in `db.go`). Existing databases without `schema_version` are auto-detected and stamped at version 1.
- **TLS for TCP connections**: when `[daemon] listen` is configured, the TCP listener uses TLS by default. On first start, the daemon auto-generates a self-signed ECDSA P-256 certificate (persisted to `tls-cert.pem`/`tls-key.pem` next to the DB file) so the fingerprint is stable across restarts. Users can provide their own cert/key via `tls_cert`/`tls_key` config fields, or disable TLS with `tls_disabled = true` for plain TCP. The daemon logs the SHA-256 fingerprint at startup. Cert generation and persistence live in `internal/api/selfsigned.go`; TLS listener wrapping is in `Server.buildTLSConfig()`. The unix socket is never TLS-wrapped.
- **TLS client TOFU (trust-on-first-use)**: the CLI performs a pre-flight TLS handshake before entering the TUI alt screen. On first connection, it displays the server cert fingerprint and prompts `Trust this server? [y/N]`. Accepted fingerprints are saved to `~/.config/bewitch/known_hosts` (one line per server: `addr fingerprint`). On subsequent connections, the client verifies the cert matches the stored fingerprint; mismatches are refused with an error. CLI flags: `-tls` (default true), `-tls-skip-verify` (bypass TOFU), `-tls-reset-fingerprint` (update a changed fingerprint). The `known_hosts` path function is a package-level variable (`knownHostsPathFn`) for test overriding. Fingerprint pinning uses `tls.Config.VerifyPeerCertificate` with `InsecureSkipVerify: true` (skip CA chain, verify fingerprint only). Code lives in `cmd/bewitch/main.go` (`resolveTLS()`) and `internal/tui/knownhosts.go`.
- **Bearer token authentication**: TCP connections can require a shared-secret bearer token via `auth_token` in the `[daemon]` config section. The server uses two `http.Server` instances sharing one mux: the unix socket server has no auth (filesystem permissions suffice), while the TCP server wraps the mux with `bearerAuth()` middleware (`internal/api/auth.go`). The middleware uses `crypto/subtle.ConstantTimeCompare` for timing-safe token comparison and returns `401 Unauthorized` on failure. Clients inject the token via `AuthTransport` (an `http.RoundTripper` wrapper in `internal/api/auth.go`) which transparently adds `Authorization: Bearer <token>` to every request. CLI flag: `-token` (or falls back to `auth_token` from config). Startup auth validation is in `DaemonConfig.ValidateAuth()` (returns `(warn, err)`): a **plaintext** TCP listener (`tls_disabled = true`) with no `auth_token` is a **fatal error** (the daemon refuses to start — the API, including destructive maintenance endpoints, would be readable/writable in the clear by any host on the network); a TLS listener with no token is a non-fatal warning (encrypted + fingerprint-pinned, but unauthenticated).
- **HTTP server hardening**: both `http.Server` instances set `ReadHeaderTimeout` (slow-loris defense) and `IdleTimeout`, and wrap the mux with `limitBody()` which caps request bodies at `maxRequestBody` (1 MiB) via `http.MaxBytesReader` (see `server.go`). `ReadTimeout`/`WriteTimeout` are deliberately left unset so long-running export/snapshot/wide-history responses aren't truncated.
- **API routing**: uses Go 1.22+ `http.ServeMux` method patterns (e.g., `"GET /api/status"`). The server always listens on a unix socket; if `[daemon] listen` is configured (e.g., `listen = ":9119"`), it also listens on TCP (with TLS by default) for remote TUI/REPL connections. The unix socket and TCP listeners use separate `http.Server` instances sharing the same mux — this allows the TCP server to wrap the mux with auth middleware while the unix socket server remains unauthenticated.
- **API serialization**: JSON only. Response types are defined in `internal/api/encode.go` (e.g., `CPUResponse`, `DiskResponse`). Handlers use `writeJSON(w, status, v)` to send responses. `writeError(w, r, status, msg)` handles error responses (keeps `r` for URL path logging on 5xx). POST endpoints accept JSON bodies. Timestamps are `int64` Unix nanoseconds.
- **TUI views**: each view is a standalone render function returning a string. Views are switched via number keys (1–8) or arrow keys. CPU, memory, disk, hardware (temperature/power), and process views show a high-resolution braille chart below live data, with time range cycling via `<`/`>`. Charts use `DrawBrailleAll()` for 4x vertical resolution and dynamic height based on terminal size. All content is wrapped in bordered panels via `renderPanel()`. The alerts view has two panels: a rules list (with cursor navigation, toggle, delete) and a fired alerts table. The hardware view combines temperature, power, and ECC into sub-sections navigated with Tab/Shift+Tab; temperature and power sub-sections have per-sensor/zone toggle selection (j/k to navigate, space to toggle, a for all) controlling which items appear on the history chart; selections are persisted in the `preferences` DB table via the API. The process view has a sortable table (c/m/p/n/t/f keys), search/filter (/), process pinning (_), and shows top N processes by CPU over time in the history chart. All system processes are visible (not just top N); non-enriched processes display `--` for FDs and cmdline columns. Pinned processes show a `_` indicator; pins are persisted via the preferences API.
- **TUI render purity**: render functions (`render*View()`, `render*Chart()`) must be pure—they receive pre-cached data and return strings, never making API calls. This is critical because `View()` is called on every frame, including navigation events like scrolling. `View()` is the sole render path—it renders content from cached Model fields and sets the viewport content on every frame. Data fetching happens only in `Update()`: the `refresh*Data()` methods fetch from the API on tick events and cache results in Model fields (`m.cpuData`, `m.memData`, etc.). History charts are pre-rendered via `regenerateHistoryChart()` and cached in `m.cachedHistoryChart` to avoid expensive chart rebuilds during scrolling. Sparkline data is similarly cached in `m.tempSparkData`, `m.netSparkData`, `m.powerSparkData`.
- **TUI staleness detection**: the Model tracks `lastDataChange map[view]time.Time`, updated in each `refresh*Data()` method when fresh (non-304, non-error) data arrives. The status bar compares `time.Since(lastChange)` against `3× maxCollectorInterval` for the current view; if exceeded, it appends `" · stale (Xs ago)"`. The threshold uses the longest collector interval for multi-collector views (e.g., dashboard). Zero time (no data ever received) does not trigger the stale indicator. `buildStatusBar()` in `styles.go` accepts the `lastChange` parameter.
- **TUI daemon-unreachable indicator**: distinct from staleness, this catches the daemon going away mid-session (which staleness alone can't, since `refresh*Data()` errors were previously only logged to the `-debug` console). `DaemonClient.getJSON()` tracks reachability centrally: a transport error from `http.Do` (connection refused, timeout, TLS failure) calls `noteUnreachable()`; any HTTP response — 200/304/even non-2xx — calls `noteReachable()`. `UnreachableSince()` (on the `daemonClient` interface) returns the first-failure time (zero = reachable). `buildStatusBar()` takes it as a parameter and, when non-zero, prepends `"⚠ daemon unreachable (Xs)"` (top priority, shown on every view including Alerts, regardless of `-debug`). `View()` also renders the gutter when unreachable even if `statusData` is nil and there are no alerts. The screenshot-capture path passes the zero time so captures never show it.
- **Fixed tab layout**: tab numbering is fixed (1–8) regardless of hardware availability. Temperature and power are sub-sections within the Hardware tab (key 6), which is always visible. Sub-sections without data show a "no data" message. The `Model.visibleTabs` slice is rebuilt by `updateVisibleTabs()` but always contains all 8 views. The active hardware sub-section (`hardwareSection`) is persisted via the preferences API.
- **TUI alert form**: pressing `n` on the alerts view opens a multi-step `huh` form for creating alert rules. The form dynamically adjusts fields based on selected metric category and alert type. Form state is managed via `alertFormState` struct in `internal/tui/alertform.go`. Pressing `e` on a selected rule opens the SAME form in **edit mode**: `fromAlertRuleMetric()` pre-populates the state from the rule (numeric fields stringified at full precision via `strconv.FormatFloat(..,'f',-1,64)`), `editID != 0` skips the category + alert-type selection steps (type is immutable), and submit calls `UpdateAlertRule` (PUT) instead of `CreateAlertRule`. The metric is locked: `origMetric` is written back verbatim so rules round-trip losslessly (incl. metrics the create form can't produce, e.g. `gpu.temperature`).
- **TUI alert form capability gating**: the create form's **Metric Category** list only offers hardware-dependent categories the host actually reports — SMART (any disk with `SMARTAvailable`), GPU (`len(gpuData) > 0`), temperature (`len(tempData) > 0`), and ECC (`eccData.Available`) — so a box with no SMART-capable disks isn't offered SMART alerts that could never fire (the engine would query an always-empty `smart_metrics`). CPU/memory/disk/network/process are unconditional. `categoryOptions(formCapabilities)` builds the filtered list; `Model.detectFormCapabilities()` (called on `n`) **refreshes disk/GPU/temperature/ECC snapshots first** because only disk data is loaded at startup — GPU/temperature/ECC load lazily on the Hardware view, so jumping straight to Alerts would otherwise hide them. A failed/empty snapshot gates the category off (safe direction). Gating is **create-only**: editing an existing rule skips the category group, so a `smart.*` rule created on capable hardware still opens for edit after a move to a VM. `buildAlertForm` takes the caps as a second arg (the edit/process-`a` paths pass `formCapabilities{}` since their category group is skipped).
- **ECC presence detection**: the ECC collector reports `ECCData.Present` (true only when EDAC memory controllers exist under `edacGlob` = `/sys/devices/system/edac/mc/mc*`, a package var for fixture tests), surfaced as `ECCMetric.Available`. Without it the zero sample (corrected=0, uncorrected=0) was indistinguishable from a host with no ECC RAM — so the Hardware tab asserted "ECC ok" on a Pi (`hasECC` now requires `ecc.Available`) and the alert form would offer ECC rules that can never fire. The mock ECC collector sets `Present: true`. ECC errors are cumulative counters, so the `ecc.uncorrectable`/`ecc.corrected` alert metrics use `MAX` over the window (like SMART, ignoring the rule's avg/max/min choice); `ecc.uncorrectable > 0` means a DIMM had an uncorrectable error. Per-mc/per-csrow localization is deferred (the metrics aggregate across all controllers).
- **TUI alert form dynamic labels**: the "Threshold Value" field's hint MUST use huh's `DescriptionFunc`/`PlaceholderFunc` (bound to `thresholdBindings(state)` = `[]any{&state.category, &state.smartMetric}`), **not** static `Description`/`Placeholder`. The form is built once with `category=""` in create mode, so a static hint is baked at build time and can never reflect the metric the user later picks — it just showed blank (and for SMART rules read as a stale CPU hint). huh re-evaluates the `*Func` variants on `updateFieldMsg` whenever the bound `hashstructure` hash changes (same machinery as the existing `OptionsFunc` alert-type selector). `thresholdDesc`/`thresholdPlaceholder` are category- and SMART-attribute-aware (`smartThresholdDesc`): a raw sector/error count hints "alert > 0" with placeholder `0`, NVMe wear hints `0-100 %` with placeholder `90`. The **SMART Attribute** select is ordered *before* the threshold group (it's appended ahead of the threshold params in `buildAlertForm`) so `smartMetric` is already chosen when the value field's hint renders.
- **TUI alerts view UX**: the rules list has a stacked **detail pane** below it (`renderRuleDetail` in `alertview.go`) showing the selected rule's full config (exact value, duration, scope, id). Delete (`d`) requires inline `y/N` confirmation (`alertConfirmDelete`/`alertConfirmName` Model fields; any non-`y` key cancels) since deleting also clears the rule's fired alerts. Create/update errors surface via `alertFormErr`. Acknowledge (`enter`, alerts panel) indexes the cached `m.alertsData` by the table cursor (not a re-fetched slice) and is synchronous so the `ack` status shows immediately. Confirm/error state is cleared on view switch.
- **TUI fixed footer (`Model.viewFooter`)**: per-view shortcut help renders in a **fixed footer outside** the scrollable viewport, so it stays visible no matter how tall the content grows — previously each view embedded its help inside a table panel, which scrolled off once the table filled the screen (on Alerts this hid the `Delete rule? y/N` prompt, so `d` armed a confirm the user couldn't see and the next key cancelled it — delete looked broken with no error). `viewFooter()` (app.go) dispatches per current view and returns the line with a leading `\n` (empty when an overlay — alert form / date picker / capture — owns the screen): **alerts** → `renderAlertFooter` (confirm prompt > form error > help, by priority); **process** → `processFooter` (sort/search/pin, active key highlighted); **network** → `netFooter` (nav + bytes/bits); **hardware** → `hardwareSelectionHelp` for the active Temp/Power/GPU section *when it has data* (ECC and empty sections: none). It's one line so it fits the `helpHeight = 2` resize-budget reservation alongside the scroll indicator. Shared by `View()` and `captureViewContent()` so screenshots match. **CPU/Memory/Disk** → the **chart-range help** (`< >:range [label]  r:pick dates`, via `m.historyRangeLabel()`), pinned to the footer rather than left inside the history-chart panel where it scrolled off (the range is still in the chart's panel title; `historyHelpInline` is removed from those three views' chart-build sites in both `regenerateHistoryChart` and the prefetch path, but kept for Network/Hardware/Process whose charts sit under an interaction footer). Dashboard has no shortcuts (no footer).
- **TUI styling**: pink & purple color palette defined in `internal/tui/styles.go`. Key colors: hot pink `#FF6EC7` (titles, active tab), soft purple `#BB86FC` (headers, borders), magenta `#E040FB` (labels), lavender `#CF6EFF` (bar fills), deep purple `#7C4DFF` (panel borders). Tab bar at top of every view; bordered panels (`lipgloss.RoundedBorder`) wrap each section. Dashboard uses multi-column grid layout on wide terminals (>120 cols).
- **TUI debug console**: launched with `bewitch -debug`. Displays a scrollable ring buffer (100 lines) of timestamped debug messages in a bordered panel at the bottom of the screen. The `debugLog` type lives in `internal/tui/debug.go`; instrumentation calls use the `m.d(format, args...)` helper (no-op when debug is nil). Panel height is resizable (5–20 lines) and scrollable. Keys: `{`/`}` scroll up/down, `(`/`)` shrink/grow panel. Instrumented points: startup config, view switches (cache hit/miss), all refresh errors, sync/async history fetches, history range changes, date picker, process pin/unpin, window resize, and the full pinned-chart pipeline (fetch → result → tab toggle → render selection).
- **Lipgloss layout**: `panelStyle` uses `Border()` and `Padding(0, 1)`. When calling `style.Width(n)`, lipgloss sets the width **including padding but excluding border**. So for a target rendered width of `W`, use `Width(W - 2)` (subtract border only, not padding). The `renderPanel()` helper in `styles.go` handles this. For side-by-side panels, use `halfWidth * 2` for full-width elements below to ensure alignment (handles odd terminal widths).
- **History API**: `GET /api/history/{cpu,memory,disk,temperature,power,process}` endpoints accept `?start=&end=` (unix seconds) and return aggregated time-series data using DuckDB `time_bucket`. Bucket size auto-scales based on range (1min–6hr). The process history endpoint uses a CTE to identify top N processes by average CPU usage over the requested period. When archiving is enabled, queries automatically determine whether to read from DuckDB, Parquet, or both based on the archive cutoff time.
- **Archive API**: `POST /api/archive` triggers manual archival; `POST /api/unarchive` reloads all Parquet data back into DuckDB, removes the Parquet files, resets `archive_state`, and clears the archive config so all queries use DuckDB only; `GET /api/archive/status` returns the `archive_state` table contents and directory statistics (file count, total bytes). CLI commands: `bewitch archive`, `bewitch unarchive`.
- **Prometheus endpoint**: `GET /metrics` (note: not under `/api/`) serves the in-memory metric snapshot in Prometheus/OpenMetrics text exposition format so an existing Prometheus/Grafana stack can scrape bewitch's hardware/ECC/power/SMART/GPU metrics. `bewitch_` prefix, dimensions as labels (`core`, `mount`, `device`, `interface`, `sensor`, `zone`, `gpu`, plus a `mode`/`kind`/`direction`/`period` label to fold related series into one family). Reads only the cache (no DB), like the live metric handlers; process series are aggregate-only (no per-pid, to bound cardinality). Hand-rolled (`prometheus.go`, `promWriter`) — no client_golang dependency. On the TCP listener it sits behind the same bearer auth as everything else (Prometheus supports `bearer_token` in scrape config). **Metric typing**: `promWriter.help()` emits a gauge TYPE; lifetime counters use `helpTyped(name, help, "counter")` + `p.counter(...)` (the line format is identical to `gauge` — only the `# TYPE` header differs, both delegate to `series()`). The `_total` families (`bewitch_network_errors_total`, `bewitch_network_dropped_total`, `bewitch_ecc_errors_total`) and `bewitch_self_uptime_seconds`/`*_total` are counters so `rate()`/`increase()` are valid; everything else is a gauge. (The old hardcoded-"gauge" header silently mislabeled every `_total` family.)
- **Daemon self-metrics**: the daemon's own health (the actual root causes of past OOM/gap incidents) is exposed on both `GET /api/stats` (`self` object, `omitempty`) and `GET /metrics` (`bewitch_self_*`). Counters: `dropped_write_batches` (write queue full), `pause_dropped_samples` (pause buffer capped), `notify_failures` (failed live notification deliveries — a failing webhook/SMTP becomes observable rather than only logged; `Engine.notifyFailures` `atomic.Uint64`, bumped in the live `(*Engine).sendNotifications` path only, NOT the manual test endpoint; read via `Engine.NotifyFailures()`), `uptime_seconds` (resets on restart). Gauges: `proc_info_cache_entries`, `write_queue_depth`/`_capacity`, `memory_heap_bytes`/`memory_rss_bytes`, `goroutines`, and `collector_consecutive_fails{collector=...}` (0 = healthy, >0 = in backoff; bounded by the fixed collector set). Plumbing: a pull callback `Server.SetSelfStatsFunc(func() api.SelfStats)` (set once at startup, mirroring `statsFn`) read on demand by both handlers — so `runtime.ReadMemStats` runs per-scrape, never per-tick. Two-bucket reality: store-resident values (`Store.PauseDroppedSamplesTotal()` — a non-zeroing lifetime accumulator since `resume()` zeroes the per-pause `bufDropped`; `Store.ProcInfoCacheLen()`) are read directly; daemon-loop-local values are published lock-free — `droppedBatches` is an `atomic.Uint64` bumped on the drop path, and `collectTick` publishes a frozen `map[string]int` of per-collector `consecutiveFails` via `atomic.Pointer` after `wg.Wait()` so the handler goroutine never races the live `scheduled` slice. RSS is read from `/proc/self/statm` on Linux (`selfRSSBytes`), falling back to runtime `Sys` elsewhere. The `bewitch stats` CLI renders a "Daemon health" section (collectors in backoff listed only when unhealthy).
- **Query API**: `POST /api/query` accepts `{"sql": "..."}` and returns `{"columns": [...], "rows": [...]}` or `{"error": "..."}`. JSON-only (no FlatBuffers). Used by `bewitch repl`. **Read-only enforcement** (`query_validate.go`, `checkReadOnly()`): parser-level validation, not keyword matching, so it catches bypass attempts like `WITH cte AS (...) INSERT INTO ...`. It enforces **two** properties: (1) the query is a **single statement** — it uses the driver's *non-context* `Conn.Prepare`, which refuses `count != 1` *before* preparing or executing anything (critical: `PrepareContext` *executes* every statement except the last during preparation, so `DELETE FROM cpu_metrics; SELECT 1` would run the DELETE during the check and then report the trailing SELECT's type — the closed bypass); and (2) the surviving statement's `StatementType()` is SELECT/EXPLAIN/PRAGMA. Regression-guarded by `TestCheckReadOnlyDoesNotExecute` (asserts the DELETE never runs). The handler converts DuckDB driver types (`time.Time`, `duckdb.Decimal`, `duckdb.Interval`) to JSON-safe values via `toJSONSafe()` in `handlers.go`.
- **Export API**: `POST /api/export` accepts `{"sql": "...", "path": "...", "format": "..."}` and exports query results to a file using DuckDB's `COPY TO`. Format is inferred from file extension (`.csv`, `.parquet`, `.json`); parquet uses zstd compression. The SQL is validated read-only via `checkReadOnly()`. Since DuckDB has no parameter binding for `COPY ... TO '<path>'`, the `format` is checked against a `{csv,parquet,json}` allowlist and the destination path is `filepath.Clean`ed and single-quote-escaped before interpolation (the `ATTACH '<path>'` calls in `store.go` use the same `quoteLiteral()` escaping). Returns `{"row_count": N, "path": "..."}`. Types: `ExportRequest`/`ExportResponse` in `encode.go`.
- **Snapshot API**: `POST /api/snapshot` accepts `{"path": "...", "with_system_tables": false}` and creates a standalone DuckDB file containing all metric and dimension data from both the live database and Parquet archives. Uses the same ATTACH pattern as `Compact()` in `store.go`. By default excludes daemon-internal tables (alerts, preferences, scheduled_jobs); pass `with_system_tables: true` (or CLI flag `-with-system-tables`) to include them for backup purposes. The `Store.Snapshot()` method pauses writes, ATTACHes the snapshot DB, creates schema, INSERTs from each metric table (UNION ALL with `read_parquet()` when archives exist), checkpoints, and detaches. `bewitch snapshot [-with-system-tables] <path>` is the CLI command. Types: `SnapshotRequest`/`SnapshotResponse` in `encode.go`.
- **REPL**: `bewitch repl` connects to the daemon via the unix socket (or TCP with `-addr`) and sends SQL through `POST /api/query`. Uses `github.com/chzyer/readline` for line editing and history (`~/.bewitch_sql_history`). Supports dot-commands (`.tables`, `.schema`, `.metrics`, `.dimensions`, `.export`, etc.), multi-line SQL (semicolon-terminated), and piped stdin for scripting. The `.export` command supports `<table> <path>` and `(<sql>) <path>` syntax with parenthesis-matched SQL parsing. EXPLAIN output is rendered cleanly (plan tree only, no column labels) via `formatExplain()`; other multiline results use expanded format via `formatExpanded()`. Code lives in `internal/repl/`.
- **Preferences API**: `GET /api/preferences` returns all key-value pairs; `POST /api/preferences` sets a single key-value pair. Used by the TUI to persist UI state (e.g., temperature sensor selection) in the `preferences` DB table.
- **JSON API**: all endpoints use JSON. POST endpoints accept JSON request bodies with `Content-Type: application/json`. Responses wrap arrays in objects (e.g., `{"cores": [...]}` not bare `[...]`). Handlers call `writeJSON(w, status, v)` directly. For errors: `writeError(w, r, status, msg)`. For status: `writeGenericStatus(w, status, msg)`. When adding a new endpoint, define a response type in `encode.go` and call `writeJSON()` with it.
- **Alert rules**: stored in the `alert_rules` DB table (not config file). Managed via TUI or the alert-rules API endpoints. The engine reloads rules from DB on every evaluation cycle.
- **Alert rule types**: threshold (metric over/under value, **aggregated over the window** — avg/max/min, see below), predictive (linear regression extrapolation), variance (memory delta rate detection — **memory-only**; `VarianceRule.Evaluate` guards `varianceMetricSupported` and errors on a non-memory metric rather than silently running memory variance under another label). Supported metrics: `cpu.aggregate`, `cpu.steal`, `memory.used_pct`, `memory.variance`, `disk.used_pct`, `network.rx`, `network.tx`, `temperature.sensor`, `ecc.uncorrectable`, `ecc.corrected`, plus the `smart.*` family. `cpu.aggregate` is `AVG(100 - idle_pct)` over the whole-CPU aggregate row (`core = -1`) — i.e. true utilization including steal/nice/irq/softirq, not just `user+system` of core 0 (a contended VPS shows high steal but low user+system, and must still trip the alert). The TUI "usage" figures use the same `100 - idle` definition and break out a `steal:` figure when non-zero.
- **Threshold semantics & wording**: each value-metric branch compares the rule's configured aggregate over `[now-duration, now]`; the SMART branches use `MAX` (reallocated/pending/uncorrectable/percent_used) or `COUNT` (unhealthy) and ignore the configured aggregate. It is **not** a sustained-for-the-whole-window check. `buildQuery` returns an aggregate label (`avg`/`max`/`min` for value metrics, `max`/`count` for SMART) so the fired-alert message names what was computed: `"cpu.aggregate avg 91.0 > 90.0 over 5m"`. The word is **over** (across the window), not "for" (sustained), mirrored in the TUI detail pane.
- **Per-rule threshold aggregate (avg/max/min)**: threshold rules carry an `aggregate` choice (`alert_rule_threshold.aggregate`, migration `000011`, `DEFAULT 'avg'`). `avg` (default, original behaviour), `max` (catch a transient spike that averages below threshold and otherwise never fires), or `min`. Only the **value metrics** (`cpu.aggregate`, `memory.used_pct`, `disk.used_pct`, `network.rx/tx`, `temperature.sensor`, `gpu.*`) honour it; the **SMART metrics keep their intrinsic `MAX`/`COUNT`** and ignore it. The engine maps it via `aggFunc(cfg.Aggregate) → (sqlFn, label)` in `rules.go` (`buildQuery` injects `%s` for the function, empty/unknown → `AVG`/`avg`); `ThresholdConfig.Aggregate` is loaded with `COALESCE(t.aggregate, 'avg')`. API: `AlertRuleMetric.Aggregate` (`json:"aggregate,omitempty"`), threshold INSERT/UPDATE/SELECT carry it, create/update default empty → `'avg'`. TUI: a separate `huh` group (huh only hides at group level) holds the aggregate `Select`, shown only for non-SMART threshold rules (`WithHideFunc` on `alertType != "threshold" || category == "smart"`); `to/fromAlertRuleMetric` round-trip it defaulting empty → `avg`; the alerts detail pane prefixes the effective aggregate for value metrics only. Back-compat: existing rows get `'avg'` from the column DEFAULT on `ALTER`, and every read `COALESCE`s to `'avg'`.
- **Predictive already-breached path**: `PredictiveRule.Evaluate` checks the latest value (`ys[len(ys)-1]`, the query is `ORDER BY m.ts`) against `ThresholdPct` **before** the slope/future-crossing math. A disk already at/over target (past crossing → `hoursUntil<=0`) or pinned flat-at-99% (`slope<=0`) used to return nil at the worst moment; it now fires `"… already at 99% (target 90%)"`. The future-crossing branch ("predicted to reach X% in N hours") is unchanged for the not-yet-breached, still-rising case. The two messages are intentionally distinct text but the engine debounce keys on `rule_name`, so a rule hovering at the boundary won't double-fire.
- **Process-rule reliability (process_down / process_thrashing)**: both rules read `process_info`/`process_metrics`, which are written only for the **Phase-2 enrichment set** (top-N by score + pinned). A non-busy or crash-looping target rarely cracks top-N, so without help the rules see no data and silently never fire. `Engine.ProcessPins()` returns every process_down/process_thrashing rule's `ProcessName`/`ProcessPattern`; the daemon's `SetRuntimePinsFunc` closure (`cmd/bewitchd/main.go`) unions these with the TUI preference pins each collection cycle, so rule targets are always force-enriched. `alertEngine` is declared before the closure and assigned later (the closure captures by pointer; nil-guarded for the startup window). **Pin matching is two-pass** (`process.go`): a comm pass via `filepath.Match` against the 15-char-truncated `comm` (catches `ProcessName` rules), then — only for pins no comm satisfied — a cmdline pass via `globMatchAny` against the full `/proc/[pid]/cmdline` (catches `ProcessPattern` cmdline globs). `globMatchAny` is anchored and lets `*` cross `/`, mirroring the engine's SQL `LIKE` so a pattern enriches exactly the processes the rule will count; cmdline is read through the same 60s-TTL cache Phase-2 uses, so the extra reads amortize and the common comm-only case does no cmdline reads. **Remaining caveat** (inherent, not a bug): a crash-loop with lifetime shorter than the collector tick can be born-and-die between samples regardless of pinning (see `ProcessThrashingRule.Evaluate`).
- **process_down sustained-absence**: `ProcessDownRule.Evaluate` honours `CheckDuration` (it previously parsed/displayed it but evaluated only the single newest snapshot, so one missed tick or a normal restart false-fired "down"). With `CheckDuration > 0` it counts matching instances **per distinct snapshot ts** across the window and fires only when the **MAX** is below `MinInstances` — a single healthy snapshot anywhere clears it, riding out a blip or a brief restart (new `start_time`, reappears within a tick or two). The per-snapshot count uses `COUNT(DISTINCT CASE WHEN pi.pid IS NOT NULL THEN (pi.pid, pi.start_time) END)`: `pm` is LEFT-JOINed on `ts` only (carries the snapshot's whole process set), the name/cmdline match sits in the `pi` LEFT JOIN's ON clause, and the CASE is NULL-safe (a bare `(pi.pid, pi.start_time)` struct of NULLs would otherwise count as a distinct value and make absent snapshots read as present). A `snaps == 0` guard prevents a startup false-fire. `CheckDuration <= 0`/unset keeps the old single-snapshot behaviour for back-compat.
- **CPU usage / steal**: the CPU collector keeps the aggregate as `core = -1` and per-core rows. `StealPct` (hypervisor-stolen time) is computed live, surfaced in the API (`steal_pct`) and TUI breakdown, **and stored** in `cpu_metrics.steal_pct` (migration `000012`, nullable — pre-migration rows are NULL and aggregates ignore NULLs). Alert on it directly via the `cpu.steal` metric (`%s(steal_pct)` over `core = -1`, honouring the rule's avg/max/min aggregate) — distinct from overall utilization (`cpu.aggregate` = `100 - idle`, which already includes steal). The TUI alert form exposes a **CPU Metric** selector (Overall usage vs Steal) when the CPU category is chosen; both store-write paths (`writeCPUTx` tx-insert and `writeCPUAppender`) persist `steal_pct`.
- **RAPL power-counter wrap**: the power collector reads each zone's `max_energy_range_uj` at discovery; on a negative `energy_uj` delta (the fixed-width counter wrapped to 0) it adds `max_energy_range_uj` to recover the real delta instead of dropping the sample, so high-draw package/core zones don't vanish from the chart under load. Falls back to skipping the sample when the wrap range is unknown.
- **RAPL zone dedupe**: `/sys/class/powercap` is a flat directory of symlinks, so every sub-domain (`intel-rapl:0:0`) appears BOTH as a bare top-level entry (matched by the `*/energy_uj` glob, named e.g. `core`) AND nested under its package (matched by `*/intel-rapl:*:*/energy_uj`, named `package-0/core`) — the same physical counter, double-counted. `discoverZones()` dedupes by the resolved real path (`filepath.EvalSymlinks` of `energy_uj`), keeping the more-qualified hierarchical name. Genuinely-distinct counters survive: multi-socket `package-1` has its own real path, and the separate `intel-rapl-mmio` control type (which exposes same-named but physically distinct counters) is disambiguated with an `mmio/` name prefix. Zones are sorted by name for deterministic dimension IDs. `powercapRoot` is a package var so the fixture-tree test (`power_test.go`) can point discovery at a symlinked temp dir.
- **Alert rules API**: `GET /api/alert-rules` lists all rules (re-joining the per-type config tables so each rule is returned fully populated / edit-ready); `POST /api/alert-rules` creates a rule; `PUT /api/alert-rules/{id}` updates name/severity + type-specific config in place (type is immutable — a mismatch is rejected 400); `DELETE /api/alert-rules/{id}` deletes; `PUT /api/alert-rules/{id}/toggle` enables/disables. **Rule names are unique**: enforced at two levels — the create/update handlers pre-check and return `409` on collision, and a DB `UNIQUE` index on `alert_rules(name)` (migration `000005`, Go migration `migrateUniqueRuleNames`, which dedups any pre-existing duplicates by renaming the higher-id rows `name #N` before creating the index). Fired alerts, the engine debounce, and delete cleanup all key on `rule_name`, so duplicates corrupt each other. Create uses `INSERT ... RETURNING id` (NOT `LastInsertId()`, which the DuckDB driver silently returns `0` for — that orphaned the config row at `rule_id=0` and the rule never fired). Update and delete run in a single `sql.Tx`.
- **Fired-alert lifecycle**: fired alerts (`alerts` table) link to a rule by `rule_name`. Deleting a rule also `DELETE`s its fired alerts (so they don't linger as orphaned, undismissable active alerts); renaming a rule rewrites `alerts.rule_name` old→new so they stay attributable.
- **Alert engine testability**: `Engine.EvaluateOnce()` runs one reload+evaluate cycle synchronously — used by the end-to-end pipeline test (`internal/api/alert_pipeline_test.go`) that creates a rule via the handler, feeds breaching metrics, and asserts an alert actually fires (the test that would have caught the `rule_id=0` bug). The engine also logs a WARN when an enabled base rule has no matching config row, surfacing orphans instead of silently skipping them.
- **Alert firing lifecycle (stateful)**: firing is edge-triggered via the nullable `alerts.resolved_at` column (migration `000009`). An alert is **active** while `resolved_at IS NULL`. `Engine.applyAlertState()` fires on the rising edge (rule breaching + no active alert), suppresses while it stays breaching (exactly one active alert per rule), and on the falling edge (no longer breaching + an active alert) sets `resolved_at` and sends a **recovery/all-clear** notification (`Alert.Resolved=true` → email subject `[bewitch] RESOLVED …`, command `BEWITCH_STATUS=resolved`). Debounce keys on the active row, **not** acknowledgement — so acking a still-breaching alert no longer spawns a duplicate next cycle (the old `acknowledged=false` debounce bug). The `?ack=false` "active alerts" query excludes resolved rows (`acknowledged = false AND resolved_at IS NULL`).
- **Dead-man's-switch**: a built-in check (`Engine.collectionStalled`, reserved `rule_name = "collection-stalled"`) fires a critical alert when the newest `cpu_metrics` sample is older than `max(2m, 12× eval interval)` — catching in-process collection stalls (a collector wedged in backoff, a stuck writer, dropped batches) that would otherwise make every rule query an empty window and look healthy. It returns nil (no fire) when `cpu_metrics` is empty so it never false-fires at startup, and resolves via the same lifecycle when collection resumes. A fully dead daemon can't fire it (the engine dies too) — that needs external monitoring.
- **Notification methods**: the `Notifier` interface in `internal/alert/notifier.go` abstracts all notification delivery. Each type implements `Name()`, `Method()`, and `Send(*Alert) NotifyResult`. The engine constructs `[]Notifier` from config at startup. `sendNotifications()` is async fire-and-forget; `SendTestNotifications()` is synchronous for the test endpoint. Supported methods: **email** (SMTP with STARTTLS/implicit TLS via `net/smtp`, or local `mail` command via `use_mail_cmd = true` for postfix/sendmail setups), **command** (arbitrary shell command with alert details as `BEWITCH_*` env vars, 10s timeout), and **shoutrrr** (`shoutrrr.go`, `github.com/containrrr/shoutrrr`) — Discord/Telegram/ntfy/Slack/Gotify/webhook/etc. from a single service URL, configured as `shoutrrr_urls = [...]` (a list of strings, not a `[[...]]` table). Shoutrrr URLs embed secrets, so `Name()`/`Dest` are redacted to the scheme only (`redactShoutrrrURL` → `discord://***`) — never log the raw URL. Config: `[[alerts.email]]`, `[[alerts.commands]]`, `[alerts] shoutrrr_urls`. Test endpoint: `POST /api/test-notifications`. TUI: `t` key on alerts view tests all configured notifiers (shoutrrr included automatically).
- **GPU monitoring**: the GPU collector has a `gpuBackend` interface (`read()`/`stop()`) with one backend per vendor, all registered in `NewGPUCollector` and merged each `Collect()`. **Intel** iGPUs via `intel_gpu_top -J` (long-lived subprocess, JSON stream); **NVIDIA** via `nvidia-smi` (point-in-time CSV) — both auto-detect their tool via `exec.LookPath`. **AMD** (`gpu_amd.go`) is **tool-free**: it reads `amdgpu` sysfs directly — discovered by globbing `amdDRMGlob` (`/sys/class/drm/card*/device/gpu_busy_percent`, which naturally excludes DRM connectors and non-AMD cards; a package var for the fixture test), reading `gpu_busy_percent` (util %), `mem_info_vram_used`/`_total` (VRAM), `hwmon/hwmon*/temp1_input` (millidegrees → °C) and `power1_average` (µW → W), and the `*`-marked state in `pp_dpm_sclk` (clock MHz); `vendor` must be `0x1002`. `stop()` is a no-op (sysfs is stateless). Name uses `product_name` if present, else `AMD GPU (cardN)`. So AMD needs no `DetectGPUHints` entry (no tool to nag about). The Intel backend runs `intel_gpu_top` as a persistent subprocess with a reader goroutine caching the latest sample; the first sample is discarded (needs prior period for deltas). GPU metrics include utilization %, frequency, power, memory (NVIDIA only), and temperature. The collector has a `Stop()` method called on daemon shutdown to kill the subprocess. GPU data is stored via a separate `SetGPUSnapshot()` API method (matching `SetProcessSnapshot` pattern). The Hardware view (tab 6) has a GPU sub-section alongside temperature/power/ECC. Alert rules support `gpu.utilization`, `gpu.temperature`, and `gpu.power` metrics.
- **Sensor/zone caching**: temperature and power collectors cache discovered sensor/zone paths and refresh every 60 seconds, avoiding expensive `filepath.Glob()` calls on every collection cycle.
- **Dimension ID caching**: dimension values (mount, device, interface, sensor, zone names) are cached in memory with IDs assigned at first sight. `ensureDimensionID()` handles inserts during Phase 1; `getCachedDimensionID()` is cache-only for Phase 3.
- **Process info caching**: `procInfoCache map[processKey]time.Time` tracks which `(pid, start_time)` pairs have been inserted into `process_info` (mapping each to last-seen time), skipping duplicate inserts for known processes. **It must stay bounded independently of retention**: it is rebuilt by `Prune()`/`Compact()`, but those are gated on optional config, so with retention unset the cache otherwise grows for the daemon's whole lifetime (a real source of multi-hundred-MB RSS growth / OOM observed on a 2GB host). An always-on goroutine in `cmd/bewitchd/main.go` calls `EvictStaleProcInfoCache(procInfoCacheMaxAge)` every `procInfoCacheEvictInterval` (15m max-age, 5m sweep) to drop entries not seen recently; `prepareProcessInfo` refreshes last-seen for all live processes each cycle so long-running ones are never evicted. Re-inserting an evicted-but-alive process is harmless (`process_info` inserts use `ON CONFLICT DO NOTHING`).
- **Process RSS units**: the process collector reads memory from `/proc/[pid]/status` via `prometheus/procfs`, which already returns `VmRSS`/`VmSize`/`VmLib`/`VmSwap` in **bytes** (it converts the kB fields internally). `memoryFromStatus()` in `internal/collector/process.go` passes them through unchanged — do NOT multiply by 1024 (a previous bug did, inflating every stored `rss_bytes` 1024×, e.g. ~1 TB for a ~1 GB process). The Phase-1 path uses `stat.RSS * pageSize` (stat.RSS is in pages) which is correct and separate.
- **Process collector two-phase pattern**: Phase 1 scans all `/proc/[pid]/stat` cheaply (PID, name, state, CPU%, RSS, threads). Phase 2 enriches only the top N + pinned processes with expensive data (cmdline, UID, FDs via `/proc/[pid]/status`, `/proc/[pid]/cmdline`, `/proc/[pid]/fd`). After Phase 1, the collector stores a lightweight `AllProcessSnapshot()` of all processes. The daemon pushes a merged snapshot (enriched + non-enriched) to the API server each cycle. `ProcessMetric` has an `Enriched bool` field to distinguish Phase 1 vs Phase 2 data in both the API response and TUI display.
- **Per-process disk I/O**: Phase-2 reads `/proc/[pid]/io` (`read_bytes`/`write_bytes` — actual storage I/O, not page-cache `rchar`/`wchar`) once per enriched process and computes bytes/sec rates against `prevIO map[int]procfs.ProcIO` (rebuilt each cycle from the enriched set, so it auto-evicts; first sample per PID yields 0). `dt` is the shared `now.Sub(c.prevTime)` already used for CPU. Stored in `process_metrics.read_bytes_sec`/`write_bytes_sec` (migration `000013`, nullable) via both write paths; surfaced as `ProcessMetric.ReadBytesSec`/`WriteBytesSec` and a combined **DISK R/W** column + `d` sort key in the process view. **Permission caveat**: `/proc/[pid]/io` is mode 0400 — the non-root `bewitch` daemon can only read it for its own processes unless granted `CAP_SYS_PTRACE` (the debian unit has `CAP_SYS_RAWIO`, not ptrace); `proc.IO()` EACCES is swallowed silently (rates stay 0, no log spam), so other users' processes read as 0/0 — indistinguishable from idle. **Not** exposed per-PID on `/metrics` (cardinality). Per-process *network* I/O is intentionally not collected — Linux exposes no per-process network counters in `/proc` (`/proc/[pid]/net/dev` is per-netns), so it would require eBPF/packet capture.
- **Process pinning**: glob patterns (`filepath.Match`) that force specific processes into Phase 2 enrichment regardless of ranking. Dual source: config file `pinned` field (static) + TUI runtime pins stored as `pinned_processes` JSON array in the preferences DB. The collector reads runtime pins via a `SetRuntimePinsFunc()` callback that queries the preferences table each cycle.
- **Live process snapshot**: the `/api/metrics/process` endpoint serves an in-memory snapshot (all processes from the collector) rather than querying the DB. The daemon calls `apiServer.SetProcessSnapshot()` after each collection cycle. This avoids DB overhead and enables all-process visibility in the TUI. The snapshot is protected by `sync.RWMutex`.
- **Metrics caching**: `SetMetricsSnapshot()` and `SetProcessSnapshot()` store raw Go structs. `getCached*()` accessor methods are pure readers (use `RLock`), except `getCachedDashboard()` which lazily composes the dashboard from cached metric components (uses `Lock`). The dashboard is invalidated on each `SetMetricsSnapshot` call and rebuilt on next access.
- **ETag change detection**: the metrics cache has a monotonic `gen` counter (incremented on each `SetMetricsSnapshot` call); the process snapshot has a separate `procGen`. Metric and process handlers set an `ETag` response header and check `If-None-Match`, returning `304 Not Modified` when data hasn't changed. History endpoints use the quantized cache key as the ETag. On the TUI side, `DaemonClient.getJSON()` sends `If-None-Match` and returns an `ErrNotModified` sentinel on 304. All `refresh*Data()` and `fetchHistory()` methods skip data replacement, chart re-rendering, and sparkline updates when they receive `ErrNotModified`.
- **History cache eviction**: the `historyCache` map entries have a 5-second TTL. A `cleanHistoryCache()` goroutine runs every 30 seconds to evict expired entries, preventing unbounded memory growth. The goroutine is stopped via the `Server.done` channel on shutdown.

## Configuration

Config file is TOML. See `bewitch.example.toml` for all options. Both binaries accept `-config <path>`. The TUI and all subcommands accept `-addr <host:port>` to connect to a remote daemon over TCP instead of the local unix socket. The daemon enables TCP listening via `[daemon] listen` (e.g., `listen = ":9119"`). TCP connections use TLS by default (auto-generated self-signed cert); disable with `tls_disabled = true` or provide your own cert/key via `tls_cert`/`tls_key`. Client-side TLS flags: `-tls` (default true), `-tls-skip-verify`, `-tls-reset-fingerprint`. For authentication, set `auth_token` in the daemon config; clients pass `-token <value>` or inherit the token from the shared config file.

## Adding a new collector

1. Define data types in `internal/collector/` (e.g., `type FooData struct{...}`)
2. Implement the `Collector` interface in a new file
3. Add cases to `store.writeSample()`, `store.writeSampleAppender()`, and `store.prepareSampleForAppender()` in `internal/store/store.go`
4. Add a new migration in `internal/db/migrations/` for the CREATE TABLE (see "Adding a new migration")
5. Add a config struct with `Interval` field to `internal/config/config.go` (with `GetInterval` method), add it to `CollectorsConfig`
6. Register the collector in the `scheduled` slice in `cmd/bewitchd/main.go`
7. Optionally add a TUI view in `internal/tui/`

## Adding a new alert rule type

1. Implement the `Rule` interface in `internal/alert/rules.go`
2. Add a case to the switch in `engine.ReloadRules()`
3. Add the metric to the appropriate `buildQuery()` method
4. Update the TUI form in `internal/tui/alertform.go` to expose the new type

## Adding a new migration

1. Create `internal/db/migrations/000NNN_description.up.sql` with the next sequential version number
2. For Go-logic migrations (data transforms), add an entry to `goMigrations()` in `internal/db/migrate.go`
3. Version numbers must be sequential with no gaps
4. SQL files can contain multiple statements (DuckDB executes them in one call)
5. Test with both fresh databases and existing databases (`make test`)

## Debian packaging

The `debian/` directory contains full packaging for Debian/Ubuntu:

- `make deb` builds the package (outputs `../bewitch_<version>_<arch>.deb`)
- Package creates `bewitch` system user/group on install
- Installs binaries to `/usr/local/bin/`, config to `/etc/bewitch.toml`
- systemd service runs as `bewitch` user with `RuntimeDirectory=bewitch` (creates `/run/bewitch/`), `SupplementaryGroups=disk` for block device access, and `AmbientCapabilities=CAP_SYS_RAWIO` for SMART device access
- Default socket path is `/run/bewitch/bewitch.sock` (world-accessible, 0666)
- Data stored in `/var/lib/bewitch/` (owned by `bewitch:bewitch`)
- Package recommends `smartmontools` for enhanced SMART disk health coverage via smartctl

To release a new version:

1. Update `CHANGELOG.md` and `site/src/pages/docs/changelog.tsx` (use `/changelog` skill)
2. Update `debian/changelog` with new version and changes
3. Run `make deb` on a Debian/Ubuntu system
4. Test with `sudo dpkg -i ../bewitch_<version>_<arch>.deb`
5. Add the new version to the docs site version dropdown in `site/src/versions.ts`
